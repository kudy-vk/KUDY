## Epic

`Epic: #95`

## Goal

Дробныя JS-змены прылятаюць на тэлефон сама пры наступным адкрыцці апкі —
без новай зборкі і без траты ліміту хмарных зборак (EAS Update, канал
sandbox). Змена native-часткі (плагіны, канфіг дадатку) не выдае хібную
OTA-абнаўку — такі мерж ідзе на звычайную хмарную зборку PHONE-02. Адкат
абнаўлення — адной камандай. У #95 гэтага шляху няма — задача дадае яго да
эпіка, не пераадкрываючы яго крытэрыі.

Спека: `docs/superpowers/specs/2026-11-17-phone-builds-eas/spec.md`.

## Acceptance criteria

1. [ ] Мерж JS-only змены ў main → у тым жа workflow публікуецца
   OTA-абнаўленне ў канал sandbox; у змержаным PR каментар фікс: «OTA
   адпраўлена, адкрый апку зноў».
2. [ ] УЛАСНІК (чалавечая праверка): адкрыў апку на тэлефоне, дакладная змена
   (тэкст/пазнака, вядомая толькі з гэтага мержа) бачная пасля перазапуску
   апкі без усталявання новага APK. Без прылады — NOT-VERIFIED, а не PASS.
3. [ ] Змена native-плагінаў/канфігу дадатку → OTA не публікуецца: правіла
   runtime compatibility праверана ахоўным тэстам правіла (не рантаймам на
   прыладзе); такі мерж ідзе на поўную зборку.
4. [ ] Адкат: адна каманда вяртае апку на папярэдняе OTA-абнаўленне; каманда
   запісана ў runbook і праверана ў хмары (пруф — выхад eas-cli).
5. [ ] Ліміт бясплатнага update-тарыфу правераны на expo.dev pricing і
   запісаны ў runbook; частыя мержы не блакіруюцца.
6. [ ] Runbook дапоўнены (#95 AC7, па-беларуску): як атрымліваць OTA на
   тэлефоне (загарнуць апку — адкрыць нанава), чым адрозніваецца ад поўнага
   білда, як праверыць бягучую версію абнаўлення.

## Out of scope

OTA для вэб-кліента; поўныя зборкі на мерж (PHONE-02); production-канал;
iOS; OTA-абнаўленні з недавераных галін PR.
