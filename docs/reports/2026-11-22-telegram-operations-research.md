## 1. Рэзюме

| Пункт | Вывад |

## 2. Сучасны стан: сігналы і прабелы

| Сігнал | Як сёння бачны ўладальніку | Прабел |
|---|---|---|
| Водгукі (зоркі 1–5 + да 3 прычын з закрытага спіса) | Уручную: psql праз MFA-адмін Supabase + `tools/feedback-report/cli.mjs` (runbook `docs/runbooks/feedback.md`) | Ніякіх алертаў: нізкая ацэнка можа тыдзень заставацца незаўважанай |

| RevenueCat webhook | HMAC fail-closed (без сакрэту endpoint не разгортваецца); падзеі — у `webhook_events` | Тыпавая паломка (сакрэт змянілі/адключылі) бачная праз тыдні |

| Версія кантэнту | Рэлізныя маніфесты ў рэпазітары | Няма «што ў стале» адным позіркам |

Вывад: няма нічога, што сама дае ведаць пра праблему. Гэта і ёсць асноўны вынік Telegram-каналу.

## 4. Форма: варыянты архітэктуры

| Варыянт | Што гэта | Закрыцце сцэнараў | Рызыкі | Абслугоўванне | Кошт | Адпаведнасць рашэнню ўладальніка 2026-11-13 (запіс у кантэксце #274) |
|---|---|---|---|---|---|---|
| **A. Супергрупа з forum topics + backend relay** | Адна прыватная група, 4 тэмы; relay worker чытае Supabase read-only і піша ў тэмы; каманды адказваюць у тэме «Аперацыі» | S1–S8 | Токен бота; набор каманд можа разрастацца — межы §7 | 1 worker на Selfer; ратацыя токена ў runbook | 0 € | Так — падтрымана ўладальнікам (запіс у кантэксце #274) |
| B. Закрыты канал (push) + асобны чат для каманд | Канал толькі для зводак; каманды ў асобным чаце | S1–S4, S6–S8; тэмы/структура горш; дзве сістэмы | Той самы токен + два чаты | Крыху вышэй (два чаты) | 0 € | Так, але структура бяднейшая |
| C. Унутраная вэб-панэль/лог-сэрвіс без Telegram (напр. uptime-kuma/Grafana на Selfer, алерты — email) | Поўны кантроль даных, нулявая перадача ў Telegram | S1, S3, S4, S6, S7 (каманды не прыродныя) | Не тэлефон-first: пуш-няяўнасць слабейшая; email алерты чытаюцца пазней | Вышэй: панэль + конфігурацыя алертаў | 0 € (Selfer) | Слабей: уладальнік падтрымаў Telegram |
| D. Гібрыд: панэль як крыніца праўды + Telegram **толькі** пуш-зводкі без каманд | Мінімальная паверхня: ніякіх каманд, нулявая рызыка каманд старонніх | S1–S4, S6; каманды S7/S8 губляюцца | Самыя нізкія | Самае нізкае | 0 € | Часткова: губляе каманды |

**Рэкамендацыя: A з дысцыплінай D.** Абгрунтаванне:

1. Каманда = 1 чалавек, які жыве ў тэлефоне: пуш-няяўнасць вырашае.
2. Тэмы = самадакументаваны архіў інцыдэнтаў і рэакцый.
3. Рашэнне ўладальніка 2026-11-13 ужо абірае супергрупу з тэмамі (запіс у кантэксце #274); C не адкідаецца — health-метрыкі для relay у будучыні можа даваць uptime-kuma на тым жа Selfer (адкладзена §13).
4. Дысцыпліна D — абмежаванні: Telegram ніколі не крыніца праўды (усё можна паўтарыць з Supabase/Selfer-логаў), каманды толькі read-only са стандартных запытаў (§7).

## 5. Структура тэм і палітыка (для A)

| Тэма | Што трапляе | Хто піша | Архіваванне |
|---|---|---|---|
| Водгукі | S1 дайджэст, S2 трыгер | relay | Па месяцы; закрытая спасылка на адмін-панэль у кожнай зводцы (S5) |
| Памылкі | S3, S4 інцыдэнты: адзін інцыдэнт = адно паведамленне + «яшчэ ×N за акно» | relay | Па месяцы |
| Статус | S6 тыднёвы дайджэст | relay | Па квартале |
| Аперацыі | Адказы каманд S7/S8 + аўтаматычныя аўдыт-нататкі (хто/што/калі) | relay + уладальнік | Па месяцы |

Політыка: у супергрупе ўключаны auto-delete тэрмінам з вердыкту D6 (кандыдат — 90 дзён). Правіла: у Telegram не захоўваецца нічога, чаго няма ў Supabase або логах Selfer — група можа загінуць без страты даных.

## 6. Патокі даных і правы

```text
KUDY (Android/iOS/web)
        │ device/events/feedback/grant/rc-webhook
        ▼
Supabase cloud (RLS deny-by-default; feedback_current/mutations, webhook_events)
        │ read-only SQL са стандартных запытаў + метрыкі лагаў
        ▼
Selfer relay worker (адзін redact-модуль фарматавання; ніякага сырога)
        │ rate-queue + dedup
        ▼
Telegram Bot API (polling; BOT_TOKEN у env Selfer)
        ▼
Прыватная супергрупа: Водгукі / Памылкі / Статус / Аперацыі (толькі ўладальнік)
```

| Паток | Даныя ў зводцы | Атрымальнік | Захоўванне | Правы |
|---|---|---|---|---|
| S1 дайджэст водгукаў | count, mean, гістаграма 1–5, тап-прычыны (коды), закрытая спасылка | уладальнік | Telegram auto-delete (D6) | адзін bot, адна група, адзін user |
| S2 нізкая ацэнка | «новая ацэнка ≤2★» + код прычыны; **без назвы мэты і без device** (дэфолт; змяняе вердыкт D3) | уладальнік | як вышэй | як вышэй |
| S3 збой API | endpoint, HTTP-код, count за акно; без тела лагаў | уладальнік | як вышэй | як вышэй |
| S4 rc-webhook | тып падзеі/код/час падзеі; **без body** (RevenueCat body можа утрымліваць email кліента) | уладальнік | як вышэй | як вышэй |
| S6 тыднёвы статус | квоты, count прылад (агрэгат), версія кантэнту, нагадка retention | уладальнік | як вышэй | як вышэй |
| S7/S8 каманды | адказ са стандартнага запыта | уладальнік | адказ у тэме; аўдыт-радок на Selfer (user, каманда, час, статус) TTL з D6 | allowlist chat_id **і** user_id |

Device IDs, mutation IDs, вольныя тэксты, IP, геа, email — пералічаны ў redact-модуле як забароненыя палі; модуль адзіны, без «выключэнняў па выпадку».

## 7. Бяспека і злоўжыванні

| Рызыка | Мера |
|---|---|
| Падмена webhook | У MVP — **polling** (адкрытага webhook-эндпойнта наогул няма). Калі пазней webhook: secret token + праверка загалоўка `X-Telegram-Bot-Api-Secret-Token` |
| Уцечка BOT_TOKEN | Env на Selfer, ніколі ў рэпазітар/лаг/issue; ратацыя — крок runbook; зона дзеяння: адна група |
| Каманда ад старонняга | Дзве ўмовы адначасова: chat_id у allowlist **і** user_id у allowlist; адмова маўкліва + аўдыт-радок |
| Спам/флуд ад relay | Rate-queue (Telegram: ~20–30 паведамленняў/хв на групу — **праверыць пры рэалізацыі**), dedup-ключ (hash payload за акно), batching |
| Ін'екцыя каманды/SQL | Каманды — рэестр са строгім парсінгам, без аргументаў-вольнага тэксту ў MVP; запыты predefined у рэпазітары; адвольны SQL, shell, доступ да сакрэтаў — забаронены ад пачатку (S10) |
| Уцечка PII | Адзін redact-модуль (§6); тэст на забароненыя палі абавязковы ў рэалізацыі |
| Telegram недаступны | Збой адпраўкі **не блакуе** feedback/API шляхі (relay адасоблены); durable чарга з drop-пасля-N (лепш страціць натафікацыю, чым праблему); у Supabase/лагах нічога не губляецца; пры аднаўленні — зводка «глушына 22:00–08:00: 2 падзеі» |
| Зміна/блакіроўка Telegram як сэрвісу | Панэль/адмін Supabase застаецца крыніцай праўды; прадукт не залежыць ад Telegram — толькі аперацыйны канал |
| Цішыняночны дзындын | Усе пуш-паведамленні `disable_notification` (без гуку), крытычнасць вызначае толькі тэма/змест — палітыка назірання ў D3 |

Залежнасці: relay не залежыць ад рэлізных цыклаў KUDY; не датычыцца мабільнага кліента, required checks і `.github/`.

## 10. Scope: MVP / пазней / не-рабіць

**MVP (пасля вердыктаў):**
- relay worker на Selfer (polling, BOT_TOKEN у env, allowlist chat+user, redact-модуль, rate-queue, durable чарга з drop, аўдыт-лог)
- супергрупа з 4 тэмамі (§5), auto-delete з D6
- патокі S1 (дайджэст водгукаў 1×/дзень), S2 (трыгер ≤2★, дэфолт без мэты), S3 (5xx/таймаўт-всплеск), S4 (rc-webhook), S5 (закрытая спасылка)
- каманды `/status`, `/feedback`
- runbook: ратацыя токена, што рабіць пры падзенні, аднаўленне пасля глушыны

**Пазней (хваля 2):** S6 тыднёвы статус (метрыкі), S8 каманды `/errors`, `/content`; uptime-kuma/панэль як health-крыніца relay.

**Не-рабіць:** S9 сырыя вольныя тэксты ў Telegram (да вердыкту D7), S10 write-каманды/SQL/shell, S11 натафікацыі білдаў (да PHONE-03), публічны канал, усякая перадача кліенцкіх даных.

## 11. Калі Telegram — НЕ лепшае рашэнне

- Каманда вырастае да >3 людзей з рознымі ролямі → панэль з правамі, Telegram застаецца толькі пуш-зводкі (D).
- Патрэбны пошук па лагах і доўгі рэтэншэн → лог-сэрвіс; Telegram тады пуш-зводкі без зместу.
- Калі ўладальнік не хоча дзяржать Selfer жывым → Supabase-cron варыянт з пашырэннем зоны сакрэтаў (§9) — гэта адзіны кампраміс.
