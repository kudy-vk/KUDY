# Праверка сапраўднага QA APK перад распаўсюдам

Гэта інструмент падрыхтоўчай задачы [QA-DIST-01 #982](#982)
для будучага працэсу #977.
Ён нічога не збірае, не падпісвае і не публікуе. Вынік `PASS` магчымы толькі
пасля праверкі **сапраўднага лакальнага APK**, Android SDK і даверанай атэстацыі.
Сінтэтычныя тэсты ў гэтым рэпазіторыі не з'яўляюцца доказам рэальнай зборкі.

## Запуск пасля зборкі

Патрэбныя Node.js, `aapt2` і `apksigner` з Android SDK Build Tools.
Пасля стварэння **падпісанага standalone QA APK** запусціць:

```sh
node tools/android-build/qa-apk-verify-cli.mjs \
  --apk /path/to/qa.apk \
  --package by.kudy.app.sandbox \
  --source-sha 1111111111111111111111111111111111111111 \
  --provenance /path/to/qa-provenance.json \
  --trusted-public-key /path/to/pinned-ci-public-key.pem \
  --metadata /path/to/release-metadata.json
```

Тут SHA і шляхі — **толькі прыклад сінтаксісу**. Замяніць SHA на сапраўдны
40- або 64-сімвальны ідэнтыфікатар зыходнага каміта, а файлы — на рэальныя
выхады даверанай зборкі. `--metadata` неабавязковы. Калі `aapt2` ці
`apksigner` адсутнічаюць у `PATH`, задаць іх давераныя лакальныя
выканальныя файлы праз `--aapt2` і `--apksigner`. Не падстаўляць
скрыпты з непацверджаных загрузак.

Валідатар правярае цэнтральны і лакальны ZIP-запісы, распакоўвае абавязковыя файлы і звярае іх памеры ды CRC32 (памер распакаваных даных абмежаваны 128 МіБ на файл). Пашкоджаны або падстаўлены запіс не лічыцца доказам наяўнасці файла. Ён патрабуе
`AndroidManifest.xml`, `classes.dex` і непусты
`assets/index.android.bundle`. Ён звярае сапраўдныя
`package/applicationId`, `versionCode`, `versionName` праз `aapt2`,
подпіс схемы v2/v3 і адзін сертыфікат праз `apksigner`, а таксама
вылічае SHA-256 файла. `by.kudy.app` і `by.kudy.app.dev` забароненыя,
нават калі карыстальнік падасць іх як чаканыя.

## Атэстацыя паходжання

**Самога commit SHA у імя APK, `eas.json`, metadata JSON ці вывадзе
інструмента недастаткова.** Для `PASS` патрэбная асобная атэстацыя, якую
давераны build-працэс падпісвае Ed25519 **пасля** атрымання канчатковых
байтаў APK. Структура `qa-provenance.json`:

```json
{
  "schema": "kudy.qa.apk.provenance.v1",
  "payload": {
    "schema": "kudy.qa.apk.provenance.v1",
    "sourceSha": "1111111111111111111111111111111111111111",
    "apkSha256": "64 lowercase hex symbols of actual APK digest",
    "packageId": "by.kudy.app.sandbox",
    "versionCode": 42,
    "versionName": "1.2.3"
  },
  "signature": "base64 of Ed25519 signature"
}
```

Значэнні ў прыкладзе не з'яўляюцца сапраўднай атэстацыяй.
Байты падпісанага паведамлення вызначае
`provenanceBytes(payload)` у
`tools/android-build/qa-apk-verify.mjs`: UTF-8
`KUDY-QA-PROVENANCE-V1\n` плюс `JSON.stringify` аб'екта з палямі
`schema, sourceSha, apkSha256, packageId, versionCode, versionName`
**у гэтым парадку**. Файл атэстацыі і адкрыты ключ захоўваюцца асобна
ад APK. Закрыты ключ — толькі ў дазволеным сакрэтным сховішчы даверанай
сістэмы зборкі. Адкрыты ключ павінен быць загадзя замацаваны аператарам
па-за недаверанымі артефактамі; калі ключ прыходзіць разам з APK і яго
ніхто не праверыў, **крыптаграфічнае паходжанне не даказана**.

Валідатар правярае подпіс атэстацыі, адпаведнасць SHA-256 рэальнаму APK
і дакладнае супадзенне зыходнага SHA, package ID і версіі. Гэта даказвае
сувязь з давераным падпісантам, але патрабуе, каб сам давераны build-працэс
сапраўды фіксаваў названы зыходны каміт; без такога кантролю
адзін файл атэстацыі не даказвае, з якога кода сабраны APK.

Неабавязковы `release-metadata.json` — JSON з пяццю палямі
`apkSha256`, `sourceSha`, `packageId`, `versionCode`, `versionName`,
якія павінны адпавядаць атэстацыі і фактычнаму APK.
Метаданыя **не замяняюць** подпіс атэстацыі.

## Вынік і бяспечнае выкарыстанне

Вывад CLI — адзін JSON-радок са `status`, `checks`, `reasonCodes`,
`apkSha256`, `packageId`, `versionCode`, `versionName`,
`signingCertificateSha256`, `source.expected` і `source.verified`.
Шляхі файлаў, ключы і поўны вывад SDK не выводзяцца. Статусы:

- `PASS`, exit `0` — усе абавязковыя праверкі пацверджаныя;
- `FAILED`, exit `1` — няправільны APK, схема, подпіс,
  несупадзенне, памылка SDK або недастатковыя файлы;
- `NOT-VERIFIED`, exit `2` — паходжанне не пацверджана
  (адсутнічаюць атэстацыя або давераны адкрыты ключ);
- exit `64` — няправільны сінтаксіс выкліку, статус `FAILED`.

**Працэс #977 мусіць спыняць публікацыю пры любым ненулявым exit code.**
Публікацыя не павінна лічыць `NOT-VERIFIED` поспехам. Калі яшчэ няма
даверанага ключа і атэстацыі, сапраўдная праверка паходжання застаецца
непацверджанай.

Для #977 па-ранейшаму патрэбныя асобныя доказы: канчатковы падпісаны APK,
падпісаны provenance ад кантраляванай зборкі, бяспечная раздача тэстарам,
праверка на фізічным Android без Metro, абнаўленне і адкат. Гэты інструмент
не заменіць іх.

## Паўтаральная лакальная праверка

```sh
node --test tools/android-build/qa-apk-verify.test.mjs
node tools/android-build/qa-apk-proof.mjs
```

Другая каманда спачатку запускае тэсты, затым у часовай копіі наўмысна
выключае блакіроўку адсутнай атэстацыі. Калі мутант **не** праваліць тэсты,
каманда завершыцца памылкай. Ніякія APK або ключы не публікуюцца; падпісаныя
APK у сінтэтычных тэстах не ствараюцца.
